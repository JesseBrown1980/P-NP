# White-first Bitcoin tail / black–white–brown alphabet funnel

## Question

The user asked whether Bitcoin's 256-bit SHA256d output and the 256-symbol
byte alphabet used in Brown's RimeSphere can be related by a reversible
alphabet translation, starting from the white-hole version of the *tail*
and reading back into black and anti-anti coloured views.

This experiment tests that hypothesis using original public Bitcoin
Genesis SHA256d, the nine-cat source-derived signed observing rule,
the 3×3 cat arrangement, and Brown's paid-Shannon information accounting.
It is stacked on the independently accepted [nine-cat exact Bitcoin
DPLL PR #65](https://github.com/JesseBrown1980/P-NP/pull/65)
without changing that full-original-CNF solver or its proof artifacts.

## Mathematically precise source

- Full Bitcoin Genesis block header = 80 bytes, SHA256d = `000000000019d6689c085ae165831e934ff763ae46a2a6c172b3f1b60a8ce26f`.
- Unknown search variable in **this bounded test** is only the
  12-bit low nonce suffix; the 76-byte header prefix and the nonce's high
  20 bits are supplied. There are 4,096 candidate headers.
- A 256-*symbol* byte alphabet represents **8 bits per symbol**.
  A 256-*bit* hash has 32 symbols and (2^{256}) possible states;
  the numerical coincidence '256' does not make inversion a trivial
  symbol translation.
- Eight exact byte-alphabet orientations are generated by three
  commuting involutions: reversing byte order, swapping nibbles,
  reversing bits within each nibble.
- **Black** = identity orientation (mask 0);
  **white** = global bitstream reversal (mask 7);
  **brown** = nibble-plus-intra-nibble reversal (mask 6).
  These are *experimental computational mappings*, not historical
  definitions of physical black and white holes.
- Their inverses are applied to every one of the 4,096 authentic SHA256d
  targets. The 32-byte output is also encoded into 192 balanced trits
  plus 24 zero padding trits, occupying eight 27-trit rooms. All 3
  ternary wave-key rotations restore the original public target exactly.

## Three recovery paths and ledger payment

1. **Path 1 retained source:** reconstruct the 80-byte public header
   from any two of A/B/P XOR banks. It stores 768 bytes in binary
   (4,608 bytes in the historical ternary-glyph representation) and
   necessarily holds the nonce.
2. **Path 2 CRT advice:** residue moduli 17/19/23 identify the
   unknown 12-bit suffix once those 3 source-derived advice bytes
   are supplied. This is a paid side-information recovery, not
   hash-only inversion.
3. **Path 3 public hash watcher:** search authentic 4,096 candidate
   headers with double SHA256d. No saved bank or CRT suffix advice
   is passed to the selector. All methods see the same fixed public
   context, target hash, and nonce domain.

Black/white/brown views are fed into the SAME three-box × three-radius
nine-cat signed observation rule. For each of 4,096 candidates per
target, six source/tail trits are sampled and nine scalar observations
are computed. The nine-cat order is descending absolute score,
tie-broken by the existing 7^i modulo 1,000,081 Fischer order.

Projected observation cost = 36,864 scalar readings and 24,576 link
reads per target; if stored explicitly, 73,728 extra bytes. An
inverse lookup table giving O(1) access to the 12-bit suffix would
require 4,096 SHA256d precomputations and at least 139,264 payload
bytes of 32-byte hash + 2-byte nonce records, plus index overhead.

Neither the byte permutations nor a seeded codebook adds unknown
nonce information. Reversing the output alphabet exactly cannot
change the solution set:

[
   f(X)=Y iff T(f(X))=T(Y)
]

for any bijective byte encoding (T).

## Hosted acceptance

The independent workflow is
`.github/workflows/pnp-bitcoin-white-first-tail-funnel.yml`:

- **28 original preselected targets:** run the actual Bitcoin
  double-SHA256 watcher for every selected candidate until the
  target matches, comparing Fischer, sequential, black, white,
  and brown candidate ordering.
- **256 additional reproducibly preselected targets:** compute all
  4,096 Bitcoin SHA256d outputs and obtain exact candidate ranks,
  without repeating every hash calculation for each ranking.
- **Independent Python referee:** independently construct the full
  4,096-source SHA256d map, every eight-point reversal, all 284
  nine-cat orientation rankings, and the Brown paid-closure ledger.
- Verify all eight variants and SHA-256 provenance; archive with
  SHA256 readback. The precise test code is stdlib Python and
  does not use trained weights, GPU, a quantum-cloning protocol,
  or an external source of unknown nonce bits.

Lower is better on this metric. Brown orientation improves over
white and black in both samples but does not consistently beat the
simpler control. One specific Genesis target has black=761 and
white=3,555 actual hashes, illustrating the variation.

This evidence establishes representation/reconstruction equivalence
and empirical candidate-order behavior **only**. The full 32-bit
Bitcoin nonce and generic SHA256d preimage problems remain open
search tasks, and the preexisting accepted nine-cat full CNF
511-node frontier is untouched.
